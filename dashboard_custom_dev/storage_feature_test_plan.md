# KX Storage 功能测试前提说明

## 1. 当前 node11 环境现状

- 节点：`node11`
- 外网 Dashboard 地址：`https://218.197.36.133:11443`
- 当前集群仅部署了以下服务：
  - `mon`
  - `mgr`
  - `prometheus`
  - `grafana`
  - `alertmanager`
  - `node-exporter`
  - `ceph-exporter`
  - `crash`

当前**未部署**以下服务：

- `osd`
- `rgw`
- `nfs`
- `smb`
- `iscsi`
- `nvmeof`
- `mds`

因此当前页面现象是正常的：

- 仪表盘“容量”为空
- 块设备、对象存储、文件存储、SMB 页面提示 `not configured`
- 这些问题不是纯前端问题，而是测试环境还没有对应后端服务

## 2. 为什么容量为空

仪表盘容量依赖集群内至少存在 1 个 OSD，并且 `pgmap.bytes_total / bytes_used` 有有效值。

当前集群为 `0 OSD`，因此：

- 容量饼图没有数据
- 集群利用率中的容量趋势没有数据
- 块设备、对象、文件相关功能也缺少最基本的数据池承载层

## 3. 当前磁盘检查结果

基于 `lsblk` 结果，当前节点可见磁盘如下：

- `oss1 / nvme0n1`
  - 存在系统分区
  - 根分区 `/` 挂载在该磁盘上
  - **这是系统盘，不能用于 OSD 测试**

- `oss0 / nvme1n1`
  - 存在多个分区
  - 当前没有挂载点
  - 但它**不是空白裸盘**，仍然带有分区表
  - 在未核对用途前，**不能默认用于 OSD**

结论：

- 当前没有可以直接判定为“安全可用”的空白测试盘
- 本轮不执行任何 `zap`、分区清理、OSD 创建动作

## 4. 后续测试实施顺序

后续要把主要存储功能测通，建议按下面顺序推进。

### 4.1 OSD 最小化测试

目标：

- 至少新增 1 个 OSD，让仪表盘容量、池、RBD、CephFS 能开始出数据

注意：

- 如果只做 1 个 OSD，集群健康和副本策略需要按测试场景单独调整
- 如果希望健康状态更合理，建议至少准备 2 块测试盘或接受单副本测试策略

执行前必须确认：

- `nvme1n1 / oss0` 是否允许清空并作为测试盘
- 或者是否会提供新的独立测试盘

### 4.2 块设备测试

前提：

- 已有 OSD
- 已创建 pool

动作：

- 创建 RBD pool
- 创建测试 image
- 执行基础读写，验证仪表盘 IOPS 与吞吐变化

### 4.3 对象存储测试

前提：

- 已有 OSD

动作：

- 部署 `rgw` service
- 创建 realm / zonegroup / zone
- 创建对象用户和测试桶
- 上传对象，验证对象存储页面与仪表盘变化

### 4.4 文件存储测试

前提：

- 已有 OSD

动作：

- 创建 CephFS 所需 metadata/data pool
- 部署 MDS
- 创建文件系统
- 验证文件存储页面

### 4.5 NFS / SMB 测试

前提：

- NFS：先有 NFS service，且后端要么使用 CephFS，要么使用 RGW
- SMB：先有 SMB service/module，且建议基于 CephFS 子卷开展测试

动作：

- NFS：创建 NFS cluster 与 export
- SMB：创建 SMB cluster、认证资源、share

## 5. 推荐的下一步

下一步最关键的是确认测试盘策略，只需要确认一件事：

- `nvme1n1 / oss0` 是否允许清空作为 OSD 测试盘

如果不允许，则需要新增一块独立测试盘。没有 OSD，这一批块设备、对象、文件、SMB 功能都无法形成有效测试闭环。
